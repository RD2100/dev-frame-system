## 6. Windows 重置后的恢复顺序

1. 重置前如需保留候选代码和临时证据，先把五个 `D:\dsh-devframe-sandboxes\*` 目录以及必要的 `D:\tmp` 证据复制到不会被重置影响的位置；D 盘可能保留不等于数据一定可用。
2. 重置后先恢复 Git、Node、pnpm 和项目依赖，再逐个候选副本执行以下预检：

   ```powershell
   Get-Location
   git rev-parse --show-toplevel
   git rev-parse HEAD
   git status --short --untracked-files=all
   ```

   预检结果必须确认路径是预期副本、基线与 `4e84901e6471b79ec0338099867ebb4606d12bb5` 一致或有明确差异说明；路径、对象库或状态不明时停止写入，不执行 `git clean`、`git reset` 或宽泛复制覆盖。
3. 修复失效的 Git `alternates`，必要时按基线重建候选工作树；每个候选副本先记录路径、HEAD、状态和关键文件哈希。
4. 不要立即同时唤醒五个组长。先由集成组按责任边界建立一份固定组合候选，纳入权限、Profile、Session 事件目录、Controller 证据和 Reliability 的明确文件；禁止整目录覆盖。
5. 先修复两个硬阻断：权威事件目录和冷恢复重复角色分配；随后补齐 peer 构建产物，并复验 Controller 冷恢复与持久化失败回滚。
6. 让 QA 在固定组合候选上只读验证：源码测试、TypeScript、lint、事件目录新鲜度、真实 AgentLoop＋Jsonl 冷恢复、打包消费者导入、Controller 证据回执和 Reliability 回归。证据必须绑定候选路径、基线、文件哈希、配置和时间。
7. QA 接受后，根协调者确认主树未被意外修改，只按精确路径提升改动到 `D:\dsh-devframe`，在主树重跑窄回归；只有根协调者可以暂存精确路径并创建一个本地逻辑提交，推送、PR、合并、发布仍需用户明确授权。

## 7. 恢复后的目标和验收门槛

恢复后应创建 successor Goal，不要把已完成、暂停或 `blocked` 的旧 Goal 当作仍在持续执行；新 Goal 至少要写明父目标、依赖、解除阻断条件和下一步动作。

状态必须按 `slice_green`、`qa_accepted`、`main_integrated`、`release_green` 分开记录；局部测试通过不等于第一阶段完成。

第一阶段只有在权限接入、Goal 启动顺序、冷恢复、失败回滚、打包消费者、Controller 证据和独立 QA 证据在同一组合候选上通过，并完成主树精确集成后，才可以宣布完成。

本文件在恢复期间只更新当前快照，不追加逐次巡检流水账；恢复完成后应把有效结论收敛回相应设计/时间线文档，再归档或删除本临时交接文件。
