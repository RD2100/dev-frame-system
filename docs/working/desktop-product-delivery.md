## Goals and requirements <a id="requirements"></a>

The user needs expert teams, Shadow, and Obsidian memory in official Desktop, with full pages to manage capabilities. Screenshots are interaction references, not evidence of existing DSH functionality.

| Scope | Expected interaction | Acceptance |
| --- | --- | --- |
| Experts and teams | Search, categories, card details, summon, example questions, selected composer tag | Summoning binds a real session and execution; results appear; Shadow keeps its entry |
| Skills and MCP | Tabs, search, installed state, enable/disable; add, edit, test, remove connectors | Reuse official runtimes and actually load and call them; responses and logs omit credentials |
| Library and memory | Recent access, local artifacts, personal files, search, preview, Vault selection, absolute-path copying, conversation references | Vault Markdown is the file source of truth; distinguish memory from source material; report edit conflicts |

Shared files and team spaces belong to later multi-user collaboration; the local single-user release cannot claim support through placeholder buttons. Shadow has its own entry, with the expert center above it.

## Collaboration and acceptance <a id="delivery"></a>

The coordinator assigns work, records progress, and reviews; workers use gpt-5.6-luna with reasoning_effort=max and do not spawn more workers. Each worker records its ID, workspace, starting baseline, exclusive paths, and check results, preserving pre-existing edits.

The coordinator exclusively schedules shared builds; workers may run focused tests verified not to write shared build directories. Review source changes before integration and relevant validation. Evidence must match the actual file revision. States distinguish pending assignment, developing, awaiting review, needs fixes, accepted, and blocked.

Each increment reports changed files, test commands and exit results, missing verification, and next actions. Source inspection or passing unit tests cannot establish Desktop usability; final acceptance needs isolated runtime loading, button execution, persistence, restart, and compatibility checks. Real-model calls follow existing authorization and remain explicitly unverified when not executed.
