# Agent Note: 持久化项目请求与修复准入

Status: implemented

[English](2026-09-07-durable-project-attempt-and-repair-admission.md) | 中文

## 问题

如果发送请求不消耗计数，请求计数器就无法限制模型流量。仅保存在一个控制器对象内的修复计数器无法约束控制器替换或重启后的反复审查。持久化证据成功、随后任务状态写入失败时，对同一失败重复计费也会消耗有用工作额度。

## 决策

[项目请求预算消费方](../../../../packages/experimental/project-controller/src/request-budget-consumer.ts)在委托 `llm/stream` 瀑布前预占一次发送尝试。宿主选定的根将实际活跃发起 Agent、其插件组长及执行 Agent 限定到同一个总控服务预算。AgentLoop 重试经过相同准入。服务串行记账，在返回前持久化每次用量；结果不确定的写入会关闭计费准入，直到服务重新加载。持久化后的取消不退还预占额度。用量表示发送准入，不表示供应商计费，也不能证明发生过 HTTP 请求。

[DevFrame 会话日志](../../../../packages/experimental/devframe/src/session-journal.ts)通过 `devframe/repair-admission` 拥有修复准入。已有负评和评级为 fail 的任务告警共用以总控会话和 Goal 为键的额度。原因引用已有审查标识或该任务唯一的持久化告警。相同重试返回原回执；Goal revision 和人类授权的 resume 保留累计用量。新 Goal 获得独立额度，已被替代的 Goal 无法通过新原因或历史回执重新开启工作。

配置项 `repairLimit` 为正整数，默认值为二，Goal 记录准入后不能改变。使用同一活跃会话的日志实例共用队列和结果不确定的刷新失败锁。权限在队列内检查，调用方只有在持久化后才能获得准入。审查证据、修复准入和任务状态推进仍是独立写入；恢复复用它们的持久身份，不假定出错意味着未发生写入。投影检查点版本三从事件日志重建较旧检查点。

[完成准入决策](2026-09-06-goal-completion-admission-seam.zh.md)和[人类命令决策](2026-09-06-command-goal-binding-host-command-surface.zh.md)分别继续拥有证据约束的完成和命令分发。本决策定义这些消费方共用的记账。

## 考虑过的替代方案

**只对供应商报告的用量计费。** 请求发出后可能永远收不到响应。等待用量无法在流量离开进程前执行准入，本地证据也无法证明供应商计费。

**统计每条负评。** 即使没有准入修复，审查仍会记录证据。它无法区分额度耗尽或后续任务写入失败，也不覆盖任务告警原因。

**把轮次放入不可变 Goal 绑定或控制器本地 map。** 本地 map 会在替换时重置。修改不可变绑定会混淆已授权工作身份和可变用量。文件绑定存储的整文档重命名能防止读者看到半份文档，但没有跨进程读取、修改、写入锁；在那里另设计数器还需要额外日志表达来支持重建。

**每个日志使用自己的队列和失败锁。** 同一活跃会话的独立消费方可能争用最后一个额度，或在其他消费方丢失刷新确认后继续写入。按会话共享队列所有权可以保留串行化，无须引入另一个项目状态服务。

## 影响

本地 Loader 测试观察实际回环 HTTP 请求，覆盖总控、组长与执行 Agent 共用准入、重试、取消和结果不确定的存储失败。真实会话测试覆盖共享日志争用、原因幂等、冷恢复、新 Goal 记账、检查点重放和权限撤销。消费方测试覆盖交付与命令路径。

Windows 上两个 TypeScript SDK 场景重放通过，三项语料检查全部通过。修复测试夹具实际修改并提交执行 Agent 文件，记录负评及幂等修复准入，然后再次交付和审查；SDK 模型只驱动 `project_integrate`。通过已构建 CLI 运行的 Python 源码 SDK 检查在黄金记录刷新和重放时均通过，确认传输事件、回调与持久日志一致。`/root/request_budget` 的独立审查通过。这些检查尚未验证 POSIX 执行或执行 Agent 与组长自主完成的开发链。

部署必须为请求消费方提供项目独占的 LLM 作用域，并为每个会话保留单一活跃写者。会话日志和总控请求队列均不提供跨进程比较交换。适配器下层的供应商 SDK 重试需要单独验证。这些本地检查不代表已启用随产品提供的 profile，也不代表生产上线。
