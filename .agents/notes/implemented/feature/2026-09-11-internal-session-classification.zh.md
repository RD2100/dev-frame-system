# Agent Note: The internal-session classification

Status: implemented

[English](2026-09-11-internal-session-classification.md) | 中文

## 问题

影子的指定会话由宿主经代理路径创建、不记录 `cwd`，因此按产品的任何含义它都不是可浏览的会话：它属于打开它的那一个专属界面。而会话浏览器只从宿主列表派生行，且空白会话在被选中的瞬间就会变得可见——于是点击影子会让指定会话以未分组的「新对话」行浮现在侧栏，在人类看来就像这次点击刚造出了一个杂项对话。

## 决策

会话可以被分类为「属于某个专属界面，而非浏览列表」。`ISessions.markInternal(sessionId)` 登记该分类并返回其撤销器；`ClientSessions` 把它盖到行上成为 `SessionSummary.internal`，而该行在列表 store、`open`、`refresh` 与历史中的行为完全不变。该分类是客户端局部的：不属于宿主列表、不跨刷新存活，也绝不触碰持久化的会话。Workspace 浏览器的 `sessionVisible` 派生把内部行从分组、单列表与搜索中一并排除，因此所有浏览面同时丢掉该行。影子入口在每次成功的状态读取时登记指定 id，并在卸载时撤销，于是拥有该入口的 Web 客户端不再看到该行，而重新部署后的指定会随之迁移。

## 落选的备选

**给持久化的会话 `origin` 分类加一个 `'shadow'` 取值。** 否决：`origin` 是持久化的 header 字段，而宿主是**恢复**已持久化的指定会话而非重建它，因此除非在恢复时改写会话 header，该标记永远到不了既有的那一行——为一个展示事实付出的面太大。

**复用注册表全局的归档集合。** 否决：归档是人类动词，具有持久且用户可见的含义，且归档集合由宿主确认；让系统分类搭它的车会把该会话误报为已归档，还能从同一个界面被撤销。

**让浏览包自己持有注册表、由影子入口注入它。** 否决：它把依赖方向倒了过来（侧栏卡片反向伸进浏览包），而且会话列表的其他消费者仍然会列出该行。

**让宿主在 `session/list` 里省掉指定会话。** 否决：那会一次性对所有客户端隐藏该行，但 `open()` 要求会话在列表内，因此会打断触发器唯一正确的路径——而且会让 sessions 域依赖影子路由器的指定。

## 后果

会话浏览器不再为「由某个已挂载插件在别处拥有的会话」长出任何一行，影子的触发器与侧栏对「指定会话是什么」也就此一致。该分类的存活期与挂载中的入口完全一致：未装影子入口包的 Web 客户端、或任何非 Web 客户端，仍会把指定会话当作普通行列出来。由于这一事实是客户端局部的，sessions 域照旧携带该行——store 依然列出它被告知的每一个会话，过滤留在消费面上。

## 测试

`tree.client.spec.ts` 钉住内部行不出现在分组、单列表与两条搜索路径中，包括它正作为当前空白选中项时。`workspace-browser.client.spec.tsx` 钉住渲染出的侧栏在分组与单列表两种模式下都不为它渲染行。`sessions-service.client.spec.ts` 钉住打标、撤销，以及行尚未到达前就做出的分类。`shadow-mount.client.spec.ts` 钉住每次成功读取都登记、卸载时撤销，以及读取失败或未指定会话时完全不登记。
