# Agent Note: 客户端组合冒烟在 jsdom 测试台上装配功能插件

Status: implemented

[English](2026-09-05-client-composition-smoke-package.md) | 中文

## 问题

用手工拼装 props 渲染单个组件的功能测试无法看到各部分是否真正组合：插件 `apply` 的接线、槽位账目注册、语言注册表席位，以及渲染出的行都藏在挂载边界之后，而确实能观察到它们的浏览器快照通道是一条许多主机都跑不了的 Chromium 门禁。需要验证装配后流程——侧栏会话列表到达行操作菜单及其会话 ID 对话框——的验收工作因此没有可在主机间移植、无密钥的归属地；而且把这样的测试放进某个功能包的 `tests/`，会让每个并行工作都编辑同一目录。

## 决策

`packages/test-support/composition-smoke` 拥有 Web 客户端的装配层冒烟层级。它的 `mountComposition()` 把[客户端测试运行时](../../../../packages/test-support/client-runtime/README.zh.md)测试台包成一次调用：在类型化 Controller 替身之上装配真实的 Cordis `Context`、`SlotRegistry`、渲染器与 `ui-session` 适配器，运行用例私有的 `provide` 回调，再在挂载的大声失败服务预检之后把一个功能插件挂到活纤程上。本包的套件以这种方式挂载真实的 ui-workspace 客户端插件，并断言组合后的表面：会话列表经生产渲染器渲染，行操作菜单打开会话 ID 对话框，槽位账目携带该条目及其语言命名空间与已声明的子槽位，语言注册表绑定该命名空间，两份随包字典保持键一致，清理会注销该条目。套件在默认单元通道中按每文件 jsdom pragma 运行，因此每台有 Node 的主机无需服务器、密钥或浏览器即可运行。

## 已考虑的替代方案

**把组合测试放进功能包的 tests。** 拒绝：功能包测试针对手工拼装的 props 验证组件行为，把组合挂载测试放进那里会把该包的测试目录变成每个跨包工作共享的编辑面；支撑层才是这个测试台已经在的地方。

**在 `apps/web/tests` 下新增 jsdom 测试。** 拒绝：该目录是浏览器快照通道，且应用装配依赖只存在于构建后 `lib` 中的 Host-for-Client 生成 Remote 贡献；测试台无需这两项成本即可覆盖同一套生产插件机制。

**只静态断言导出面与字典文件。** 拒绝：可导入的导出证明不了组合——注册了任何东西的挂载、或从不打开的对话框都能通过静态检查；这一层级的价值正是观察到的装配行为。

## 后果

单元测试与手工 props 看不见的客户端装配回归，现在会在所有主机的普通单元通道中失败，验收清单可以把一条无密钥命令当作组合证据来引用。代价是多一个 tsconfig 镜像 client-runtime 引用闭包的支撑包，以及一个替身仍会对未打桩调用大声失败的测试台——冒烟保持窄面是有意为之：它钉住组合而非功能广度，后者仍归功能测试与浏览器快照通道。
