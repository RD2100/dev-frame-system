# Agent Note: 基于 DSH 原生能力的 DevFrame 开发流程

Status: proposed

[English](2026-09-02-devframe-dsh-native-development.md) | 中文

## 问题

所需产品要支持有人监督的多 agent（智能体）开发、跨项目协调和可复用记忆。DSH 已经提供会话、工具、持久化和实验性 Teams，而旧 DevFrame 工作目录把有用功能与用户明确不愿延续的治理内核混在一起。

## 提案

围绕原生扁平 Teams 组合一个 DSH 功能插件与 profile。Shadow 保持独立路由会话，每个项目拥有自己的控制器根会话，仅增加角色限制、完成校验、跨根投递和可选 Markdown 记忆。

用户要求的[总体设计](../../../../docs/generalDesign.zh.md)、其链接的四个详细设计部分，以及[验收参考](../../../../docs/testAndAcceptance.zh.md)负责定义拟议行为和交付顺序。本文只记录取舍，不是另一份实施计划。本次文档变更不替代既有 DSH 决策，也不声明运行时功能已经实现。

## 考虑过的替代方案

**复用旧 DEV 治理内核。** 这与用户明确规定的范围冲突，也会引入首个有用开发流程不需要的审批／状态机制。仅将小型功能行为及其测试作为参考。

**先构建新的编排器和网关。** 这会重复原生会话、成员表、邮箱和任务的职责。只有确实出现多进程或外部客户端需求、需要独立传输时才重新考虑。

**只用提示词描述全部限制。** 提示词可以描述角色行为，但无法强制工具权限、真实进程终止、幂等投递或绑定快照的验收，因此仍需要小型确定性策略实现。

## 验收标准

先验证[验收参考](../../../../docs/testAndAcceptance.zh.md)选定的单项目范围：角色 guard、Goal／任务／证据归属、安全停止／恢复和人工操作流程。之后用 3—5 个真实任务与直接单 agent 使用做比较，记录用户的价值判断。多项目和记忆章节是候选扩展，不是冻结待办清单；展开它们需要单独决定。

## 风险

实验性 Teams 需要固定组合与子选项传递；`tools.restrict()` 不限制本地作用域 Team 注册，因此还需要原生单调 guard。一个包仍包含指纹、写入所有权、恢复与预算等实际工作。Windows／进程内约束不提供恶意代码隔离。实际可用性与人工干预减少，在试用之前都尚未得到证明；技术检查通过本身不能成为增加角色或功能的理由。 跨根投递不保证任意外部副作用恰好发生一次。恢复与回退必须保留兼容的必需事件读取器，未经人工授权不能续跑旧工作。
